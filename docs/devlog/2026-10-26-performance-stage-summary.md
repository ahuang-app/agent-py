# 阶段小结：RAG 检索性能测试与优化（2026-10-24 ~ 10-26）

> 背景：在完成功能测试体系后，用户提出面试导向的补充需求——"功能测试都是基于状态的，性能提升也需要测试"。本阶段交付一套**性能测试方法论 + 一次完整的真实优化闭环**，所有数字可复现。

## 一、阶段目标与方法论

**目标**：把"系统功能可用"升级为"性能有基线、瓶颈有定位、优化有对比数字"。

**方法论四步**（已写入测试指南第 7 章）：

```
定义指标 → 建立基线 → 定位瓶颈 → 单变量优化后对比
```

性能测试纪律：单变量、多次取中位数、合成基准与端到端分开、记录环境、区分实测与推断。

## 二、瓶颈定位（读代码排查）

对可疑点逐一排查，排除法收敛：

| 疑点 | 排查结论 |
| --- | --- |
| `/ready` 依赖检查串行 | ❌ 误报——代码已是 `asyncio.gather` 并行（Milvus 11s 为首连初始化，属预期） |
| 向量召回与 BM25 未并行 | ❌ 已是 `asyncio.gather` 并行 |
| MCP 工具发现每请求网络往返 | ⚠️ 存在但语义复杂，列为后续优化项 |
| **BM25 关键词召回每查询重建** | ✅ **主瓶颈**：每次查询都 ① 从 Milvus 拉取该租户全量 chunk ② 全语料重新分词 ③ 重建 BM25L 评分器——三者均为 O(语料) 的每查询固定成本 |

## 三、优化实现：BM25 语料缓存

新增 `apps/backend/src/super_ai/retrieval/corpus_cache.py`（`Bm25CorpusCache`）：

- **缓存粒度**：按 `(owner, knowledge_base_ids)` 缓存 chunk 列表、分词结果与 BM25L 评分器三件套；
- **失效机制**：索引任务成功与文档删除两个向量变更点显式失效（`invalidate`），TTL 仅作遗漏路径兜底——失效正确性优先于 TTL 惰性；
- **语义正确性关键点**：带文档/元数据过滤的查询**不复用**全量评分器，而是按过滤后子集重建——保证 BM25 的 IDF 统计语义正确（缓存最容易做错的地方）；
- **接线**：`create_app` 持有共享实例注入四条链路（chat Agent、AIOps 诊断、文档索引、检索工具）；无缓存注入时行为与优化前完全一致（向后兼容）。

重构配合：`hybrid.py` 拆出 `rank_bm25_tokenized`/`build_bm25_scorer` 支持预分词语料；`tool.py` 提取 `_chunk_matches` 谓词使 chunk 过滤与 token 过滤同步。

## 四、三层证据链（数字全部可复现）

### 4.1 微基准（合成语料，隔离纯算法路径）

`scripts/bench_retrieval_bm25.py`，5 次取中位数，约 320 字/条中文运维语料：

| 语料规模 | 优化前 ms/查询 | 优化后 ms/查询 | 加速比 |
| --- | --- | --- | --- |
| 100 条 | 11.22 | 0.70 | 16.0× |
| 500 条 | 59.55 | 4.28 | 13.9× |
| 1000 条 | 128.51 | 9.28 | 13.8× |

**可信度加固**：应对"合成语料同质"的质疑，补做了多样化语料对照实验（每条不同服务/故障/术语组合），加速比 13.4×~15.0×，结论对语料多样性不敏感。

### 4.2 端到端真实管线 A/B（120 份真实文档）

`scripts/bench_retrieval_e2e.py`：120 份多样化运维手册经**真实 API 上传**、**真实 Qwen embedding + Milvus 索引**（durable 后台任务逐份完成），再以真实 embedding/Milvus/rerank 全链路 A/B（8 查询中位数）：

| 路径 | 中位延迟 | 说明 |
| --- | --- | --- |
| 优化前（无缓存） | 1826.4 ms/查询 | — |
| 优化后（冷启动） | 1392.1 ms | 含缓存填充，仅首次 |
| 优化后（热查询） | **1153.2 ms/查询** | 稳态 |

**每查询节省 673.2ms（37%）**。关键洞察：被消除的 Milvus 全量拉取在真实链路中的成本**远超**纯算法部分（微基准测不到）；连冷启动都比无缓存快，因为填充成本只付一次。

### 4.3 数据来源与推断的诚实边界

- 微基准语料为**程序化合成**（可控规模梯度、可复现）；端到端为**真实管线真实文档**；
- "消除 Milvus 拉取"在微基准阶段是读代码推断，端到端 A/B 将其转化为实测；
- 绝对毫秒数依赖本机环境，**加速比/百分比**更可迁移；
- 端到端延迟仍由 embedding/rerank 的 API 调用主导（数秒级中的大头），本优化的核心价值是**复杂度形状**（每查询成本从随语料线性增长变为与语料无关）与 Milvus 负载削减。

## 六、过程中的工程发现（顺带验证的系统能力）

1. **Docker 基础设施自愈**：跑基准期间 Docker Desktop 自行退出导致 Milvus 失联、批量索引任务失败——恢复后 durable job 语义让全部任务重试续跑成功；
2. **SQLite 写锁竞争**：worker 高频写任务状态时，轮询 GET 偶发瞬时 500——基准脚本做容忍重试（也提示了后续可给只读路径加 busy_timeout 的小优化）；
3. **基准脚本工程化**：幂等重入（409 复用已上传文档）、超时保护、失败显式而非挂死。

## 七、已识别未实施的优化项（后续路线）

1. **MCP 工具发现按用户缓存**（对话链路，预计省每请求数百 ms，需权衡工具新鲜度）；
2. **KaTeX 动态分包**（约 280KB 移出主 bundle，改善首屏）；
3. **Milvus 首连预热**（消除 `/ready` 与首次检索的建连延迟）；
4. 检索质量-延迟权衡实验（Milvus `ef` 参数、rerank 候选数）——需要召回率基准配合。

## 八、面试叙事要点（一段话版本）

> 我用"指标→基线→瓶颈→单变量对比"的方法给 RAG 检索链路做性能测试：读代码发现关键词召回每次查询都要从 Milvus 拉全量语料、全量重分词并重建 BM25L（O(语料)/查询）；实现租户级语料缓存（索引/删除显式失效 + TTL 兜底 + 过滤子集重建保证 IDF 正确）后，微基准 13.8×（多样性对照稳健），再用 120 份真实文档走真实 embedding/Milvus/rerank 管线做端到端 A/B，每查询 1826ms→1153ms（省 37%）——两层基准互相印证，且诚实区分了实测与推断、绝对值与可迁移比值。
