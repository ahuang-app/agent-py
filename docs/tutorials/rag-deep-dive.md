# 从零讲透 RAG 系统：七步全链路 + 高频面试题精解

> 本文基于 2025–2026 年公开面试题库、开源面试仓库与技术社区深度文章的检索整理（来源见文末），按"离线索引 + 在线推理"两条主线拆解 RAG 的 7 个核心步骤。每道面试题按统一框架展开：**题目 → 面试官在考什么 → 新手答法 → 高手思路 → 落地要点**。

## 开篇：RAG 是什么，为什么必须存在

RAG（Retrieval-Augmented Generation，检索增强生成）= **先检索、后生成**：把用户问题先去知识库里检索相关片段，再把片段作为上下文交给大模型"看着资料答题"。

它解决 LLM 的三个根本问题：

1. **知识截止**：模型只认识训练截止日期之前的数据，问它之后的事它只能编。
2. **私有数据不可达**：企业的运维手册、内部 wiki 从未进入任何训练集，模型一无所知。
3. **幻觉**：即便模型"不知道"，它也倾向于生成一段看起来合理的答案——RAG 用"给定资料"约束生成，并为答案提供可追溯的出处。

**RAG vs 微调**（高频开篇题）：微调改变模型的行为与风格（怎么说），RAG 改变模型能看到的事实（说什么）。判断标准：知识频繁更新→RAG（重新索引即可，分钟级）；要改变领域语感/输出格式→微调；两者不互斥，生产上常组合（微调打底、RAG 供料）。成本上 RAG 无需训练算力、可溯源、可随时下架某份文档，这些都是微调做不到的。

## 全链路总览

```
离线索引线：文档解析 → 分块 → Embedding → 写入向量库
在线推理线：问题 → (改写) → 混合检索 → RRF 融合 → Rerank 精排
            → 上下文组装 → LLM 生成(带引用) → 评估与迭代
```

## 1. 文档处理与解析

**步骤讲解**：把 PDF/Word/HTML/扫描件转成干净、结构保留的纯文本。这是整条链路的"垃圾进垃圾出"开关——解析丢掉的表格、错乱的阅读顺序，后面全部无法挽回。难点：扫描件要 OCR、表格要结构化（跨页断裂、合并单元格是重灾区）、双栏 PDF 阅读顺序还原、页眉页脚噪声清洗。

**面试高频问题**

### Q1.1【基础】PDF 里有表格和图片，RAG 系统怎么处理？

- **考什么**：是否理解"解析不是转文本"而是结构重建。
- **新手答法**："用 PyPDF 提取文本。"
- **高手思路**：区分两类元素——表格转 Markdown/HTML 保留行列关系（甚至用 LLM 把表格改写成自然语言描述并保留上下文）；图片走 OCR 或多模态模型提取描述文字；关键是"语义可检索"而不是"字符存在"。
- **落地要点**：MinerU / DeepDoc / PaddleOCR / Unstructured 四类主流方案选型；合并单元格与跨页表格要后处理规则兜底。

### Q1.2【高频】扫描件的噪声怎么治理？

- **考什么**：有没有真实处理过脏数据。
- **新手答法**："做 OCR 就行。"
- **高手思路**：OCR 只是第一步；版面分析还原阅读顺序、置信度过滤（低置信度片段丢弃或人工复核）、正则清洗页眉页脚/水印/乱码，并把"来源页码"写进 metadata 便于溯源。
- **落地要点**：建立解析质量抽检集（每类文档抽 N 页人工核对），解析器升级前后跑对比。

## 2. 文本分块 Chunking【必考模块·加深】

**步骤讲解**：把长文档切成检索粒度的片段。分块决定 RAG 质量上限：太大→一个 chunk 混多个主题，检索不精准且挤占上下文窗口；太小→语义不完整，答案断章取义。

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 固定长度+重叠 | 每 512 token 切一刀，重叠 10-20% | 简单可控 | 切断语义 |
| 递归分块 | 先按段落→句子→字符逐级回退 | 尊重自然边界 | 参数仍靠拍 |
| 结构分块 | 按 Markdown 标题/HTML 标签切 | 保留文档结构 | 依赖文档规范 |
| 语义分块 | 相邻句 embedding 相似度骤降处断开 | 语义完整 | 每 chunk 都要向量化，成本高 |
| Small-to-Big | 用小 chunk 检索、返回其所属大 chunk/父文档 | 检索准+上下文足 | 需要维护父子映射 |

### Q2.1【基础·一深挖就露馅】chunk_overlap 为什么存在？设 50% 会怎样？

- **考什么**：是否理解 overlap 的真实作用机制，还是背参数。
- **新手答法**："让块之间有连续性。"（说不清机制就露馅）
- **高手思路**：overlap 是为了**防止关键信息恰好被切断在边界上**（比如一个术语的定义跨两块，两块单独都不完整）。但 50% 重叠意味着存储和索引成本近乎翻倍，且同一内容出现在多个 chunk 里会干扰排名（多块高度相似互相挤占 Top-K）；业界常见 10–20%。有基准测试（Reddit 7 种策略实测）直接打破了"512+50"的迷信——最优参数强依赖语料。
- **落地要点**：用固定长度时重叠必须小于块长的一半才有意义；最优块长用评测集（Recall@K）网格搜索，不要抄默认值。

### Q2.2【进阶·架构取舍】为什么不能机械按固定长度切？语义分块就一定更好吗？

- **考什么**：权衡思维，而不是追新名词。
- **新手答法**："语义分块更先进所以用语义分块。"
- **高手思路**：固定分块的问题是"语义完整性"（一个步骤列表被切成两半）；但语义分块本身有三个代价——每句都要 embedding（索引成本数倍）、阈值难调（相似度断点因语料而异）、对短文档过碎。生产上更稳的是**结构优先**：有 Markdown 标题就按标题切，无结构再退到递归分块；真正的通用解是 Small-to-Big（检索粒度与上下文粒度解耦）和延迟分块（先全文 embedding 再切块，保留跨块上下文）。
- **落地要点**：按文档类型路由分块策略；chunk metadata 记录策略与参数，保证可追溯可回滚。

### Q2.3【生产排障】用户反馈"答案总是断章取义"，怎么定位是不是分块的锅？

- **考什么**：系统化排障路径。
- **新手答法**："把 chunk 调大一点。"
- **高手思路**：先分层定位——检索侧看命中的 chunk 本身是否语义完整（不完整→分块问题）；chunk 完整但答案截断→生成侧上下文组装问题。再用"应命中 chunk 标注"的评测集量化：Recall 低但命中的块是完整的→分块边界切坏了关键内容；Recall 高但答案差→看生成。
- **落地要点**：建立 bad case 归因表（检索 miss / 块不完整 / 排序错 / 生成幻觉四类），每类对应不同层的修复。

## 3. Embedding 与向量化

**步骤讲解**：把文本映射为高维语义向量，语义相近则向量相近。三个决策点：模型选型（中文场景 BGE 系列是常见答案）、维度取舍（768/1024 常够用，维度翻倍存储与检索成本也翻倍，Matryoshka 嵌套向量可降维）、索引算法（HNSW vs IVF）。

### Q3.1【高频】MySQL 存向量为什么不够？HNSW 和 IVF 分别解决什么问题？

- **考什么**：对向量检索底层约束的理解。
- **新手答法**："MySQL 不支持向量。"
- **高手思路**：MySQL 能存（JSON/BLOB）但**没有 ANN 索引**——语义相似度搜索需要的是"高维空间近邻查询"，LIKE 是字符串模糊匹配，完全不搭界；暴力全表扫 O(N) 距离计算在百万级向量下不可接受。HNSW 是跳表式多层图索引：查询快（对数级）、内存占用高、构建慢，适合读多写少；IVF 先聚类分桶、查询只扫附近 nprobe 个桶：内存省、需训练、靠 nprobe 调精度/延迟权衡，适合大规模数据。二者都在用"近似"换速度（ANN），这是向量库的本质。
- **落地要点**：数据量 <10 万可先用 faiss/SQLite 扩展；生产级选型看内存预算与 QPS；本项目用 Milvus HNSW（M=16, efConstruction=200, 查询 ef=64）——ef 越大召回越高延迟越高，是可直接调的权衡旋钮。

### Q3.2【进阶】Embedding 模型升级了，旧向量怎么办？

- **考什么**：有没有想过索引的生命周期。
- **新手答法**："换模型重新算。"
- **高手思路**：不同模型的向量空间**互不兼容**（旧查询向量 × 新文档向量 = 无意义距离），必须全量重嵌入；生产的做法是双集合灰度迁移——新集合建好、影子流量对比 Recall、切流、下线旧集合；同时利用多租户过滤字段（tenantId/kbId）做分批重建，避免全库锁。
- **落地要点**：embedding 模型版本写入 chunk metadata；重建走 durable 任务可断点续跑（本项目的索引任务运行时天然支持）。

## 4. 检索策略：混合检索【必考模块·加深】

**步骤讲解**：纯向量检索有盲区——对**精确标识符**不敏感：搜 `NullPointerException`、traceId、错误码、产品型号时，语义相近的内容可能把真正的精确匹配挤出 Top-K；反过来 BM25 关键词检索不懂同义改写（"连接池耗尽"搜不到 "pool exhausted"）。生产标配是**双路并行 + 融合**：

| 路 | 原理 | 强项 | 弱项 |
|---|---|---|---|
| 向量（密集） | 语义嵌入近邻 | 同义改写、跨语言、模糊意图 | 精确串、生僻词、编号 |
| BM25（稀疏） | 词频×逆文档频率 | 精确术语、类名、错误码 | 不懂同义、OOV 词无效 |

### Q4.1【基础·一深挖就露馅】为什么要 RRF 融合？直接把两路分数加权求和不行吗？

- **考什么**：是否理解融合的数学障碍。
- **新手答法**："RRF 效果好。"
- **高手思路**：BM25 分数（无界，可能 0~30）和余弦相似度（[-1,1]）**量纲完全不同**，直接加权必须先归一化，而归一化参数依赖分数分布、随语料漂移，调参噩梦。RRF 只用**排名**不用分数：`score = Σ 1/(k+rank)`，k 取 60——量纲无关、无需调参、对单路失效稳健（一路全 miss 时另一路排名仍有效）。这是"简单方案赢过精细方案"的经典案例。
- **落地要点**：融合的确定性要保证（同分平局用稳定键排序），否则同一查询两次结果不同，用户感知为"随机"。

### Q4.2【进阶】Reranker 能找回召回阶段漏掉的文档吗？

- **考什么**：对两阶段架构边界的清醒认知。**这是区分度极高的一题。**
- **新手答法**："能，rerank 更准。"
- **高手思路**：**不能**。Rerank 只在召回给出的候选集内重排——召回 miss 的文档根本不在候选里，精排无米下锅。这句"召回决定上限、精排决定逼近上限的程度"是两阶段检索的纲。所以检索质量的优化次序必须是：先修召回（混合检索、查询改写、调 ef），再调精排。
- **落地要点**：定位"该命中没命中"的问题永远先看召回侧（本项目的引用卡片同时展示向量排名与 BM25 排名，就是为了让"哪路没召回"可见）。

### Q4.3【生产排障】混合检索上线后几乎没提升，怎么回事？

- **考什么**：是否有"手段服务于目标"的意识，而非堆技术。
- **新手答法**："再调调权重。"（用了 RRF 根本没权重可调——这答案直接暴露没做过）
- **高手思路**：Reddit 上有真实案例：如果查询都是自然语言问句、语料没有精确标识符，向量一路已足够，BM25 增益趋近于零。先做**分查询类型归因**：精确串类查询占比多少？对这类查询单独对比两路 Recall，增益为零说明你的场景不需要混合检索（或需要的是查询改写）。
- **落地要点**：任何检索组件上线都要带 A/B 或离线评测，"业界标配"不等于"你的场景需要"。

## 5. 重排序 Rerank【必考模块·加深】

**步骤讲解**：召回（Bi-Encoder，可预计算、快、粗）之后、生成之前，用 Cross-Encoder 对候选逐一精细打分——把 query 和文档**拼接后联合编码**，能捕捉交互级的细粒度相关性，但每对都要跑一次模型，无法预计算。

| | Bi-Encoder（召回） | Cross-Encoder（精排） |
|---|---|---|
| 打分方式 | 两向量距离 | query+doc 联合编码 |
| 可预计算 | 是（文档向量离线算好） | 否 |
| 精度 | 中 | 高 |
| 适合 | 百万级粗筛 | 几十条精排 |

### Q5.1【基础】为什么不全量用 Cross-Encoder 检索，一步到位？

- **考什么**：性能与精度的分层设计。
- **新手答法**："太慢了。"（对，但要说出量级）
- **高手思路**：百万文档 × 每对一次完整 Transformer 前向 = 不可行；两阶段的本质是**漏斗**：便宜的 Bi-Encoder 从 10⁶ 筛到 10¹，贵的 Cross-Encoder 只对 10¹ 精算。这也是数据库"粗排-精排"、推荐"召回-排序"的通用范式。
- **落地要点**：候选集大小是延迟/质量旋钮——Top-20→Top-5 是常见配置（本项目即 20 进 5），候选翻倍精排耗时近似翻倍。

### Q5.2【进阶】Rerank 候选集设多大？凭什么？

- **考什么**：有没有数据支撑的决策习惯。
- **新手答法**："20 吧，大家都用 20。"
- **高手思路**：候选数的下界由**目标 Recall@5** 反推：若召回 Top-20 的 Recall@20 已达目标，20 就够；若目标文档常落在 20 名外，扩大候选才有意义——这只能用评测集算出来。同时上限受延迟预算约束（精排是在线路径，用户在等）。
- **落地要点**：画"候选数–Recall@K"曲线找拐点；拐点后增大候选只涨延迟不涨召回。

### Q5.3【生产排障】加了 Rerank 后答案质量反而下降，可能原因？

- **考什么**：对组件质量与组合逻辑的怀疑精神。
- **新手答法**："换个 rerank 模型。"
- **高手思路**：三类根因——① rerank 模型与语料域不匹配（通用 rerank 对垂直领域打分失真）；② 排序信号单一化：原来 BM25/向量各自的第一名互相制衡，rerank 后变成单模型独裁，它系统性偏好的内容类型垄断 Top-K；③ 域名/格式偏差：rerank 对长 chunk 打分系统性偏高。验证方法：对比 rerank 前后的 Recall@5 与 MRR——MRR 升 Recall 降说明它只是重排了原本就在的，还挤掉了真目标。
- **落地要点**：rerank 前后的排名都保留可查（本项目每条引用同时带 rerankRank 和原始各路排名，就是为了这种归因）。

## 6. 生成与幻觉治理【必考模块·加深】

**步骤讲解**：把精排后的片段组装进 Prompt 让模型作答。治理手段分层：Prompt 约束（"仅根据参考资料回答，资料不足以回答时明确说不知道"）、引用标注（每条结论标注来源 chunk）、温度调低（0~0.2，减少自由发挥）、阈值兜底（最高相关分数低于阈值直接返回"未找到相关内容"而不是硬答）、后置自校验（用另一次 LLM 调用核对答案是否被资料支持）。

### Q6.1【基础·一深挖就露馅】把 temperature 调到 0 就没有幻觉了吗？

- **考什么**：对幻觉根因的理解——这是"看起来简单一深挖就露馅"的典型。
- **新手答法**："低温减少幻觉。"
- **高手思路**：temperature 只控制**采样随机性**；幻觉的根因是模型的知识缺口与"必须给出答案"的倾向，贪心解码（T=0）一样会一本正经地编。低温能减少的是"同一问题两次答案不同"的抖动，不能消除" confidently wrong"。真正的治理在检索质量 + Prompt 约束 + 允许拒答 + 后置校验的组合。
- **落地要点**：T 设 0~0.2 是必要非充分条件；验收标准里加"知识库无相关内容时必须明确拒答"。

### Q6.2【进阶】检索召回了正确内容，模型仍然乱答，问题出在哪一层？

- **考什么**：分层归因能力，幻觉题里区分度最高的一问。
- **新手答法**："模型不行。"
- **高手思路**：四层排查——① 上下文组装：正确 chunk 是否真被放进 Prompt（截断、条数限制、组装 bug）？② 位置：关键信息在长上下文中部被"lost in the middle"忽略？③ 指令：Prompt 有没有明确"仅基于资料"与拒答许可？④ 模型：指令遵循能力不足（小模型常见）。前三层都排除了才轮到换模型。
- **落地要点**：把"检索命中但答错"单独建一类 bad case（与"检索 miss"分开统计），这类问题的修复成本通常远低于换模型。

### Q6.3【生产排障】幻觉率从 30% 降到 12%，你的组合策略是什么？

- **考什么**：能不能给出有数字、有主次的治理路径，而不是罗列手段。
- **新手答法**：列举"prompt 约束+引用+低温+……"全家桶，无主次。
- **高手思路**：先归因再下药：30% 里若 2/3 是"检索没命中导致的编造"——治理检索（混合检索/查询改写）收益最大；剩下"命中仍编"的用 Prompt 拒答许可+引用标注压；最后用忠实度评估（LLM-as-judge 核对答案句是否被资料支持）建立回归。顺序错了（先调生成端）会事倍功半。
- **落地要点**：每一步降多少要有评测数字；幻觉率本身用固定评测集 + LLM 评判流程定期跑。

## 7. 评估与迭代【必考模块·加深】

**步骤讲解**：RAG 是"检索+生成"两级串联系统，**必须分轨评估**——混合指标会互相掩盖瓶颈。

| 轨道 | 指标 | 衡量什么 |
|---|---|---|
| 检索 | Recall@K | 目标文档是否进了前 K |
| 检索 | MRR | 目标文档排得多前（首条相关排名倒数均值） |
| 生成 | 忠实度 Faithfulness | 答案是否被检索内容支持（RAGAS 核心，反幻觉） |
| 生成 | 答案相关性 | 答案是否回应了问题 |

### Q7.1【基础】为什么 Recall@K 和 MRR 要一起看？

- **考什么**：指标语义的真实理解。
- **新手答法**："都是检索指标。"
- **高手思路**：Recall@5=100% 但目标文档全在第 4、5 位——MRR 低，rerank 之前的体验差（如果后续只取 top-3 就漏了）；MRR 高说明不仅命中还排得靠前。Recall 是"找没找到"，MRR 是"放得多前"，分别对应召回层和排序层的质量。
- **落地要点**：检索优化前后用同一评测集对比这两个数；调 ef/候选数这类参数时 MRR 是最敏感的信号。

### Q7.2【高频】离线指标很漂亮（0.85），上线用户仍不满意，为什么？

- **考什么**：离线/在线一致性意识。
- **新手答法**："再调调模型。"
- **高手思路**：评测集与真实查询分布漂移——评测集是整理过的标准问句，真实用户是口语、带错别字、多轮指代（"它怎么配？"）；解法是把线上真实查询（脱敏）回流进评测集，加查询改写评测轮；同时上线在线信号（用户点踩率、引用展开率、追问率）作为北极星。
- **落地要点**：离线集合每季度用线上样本刷新；两个数字（离线分、在线满意率）都盯。

### Q7.3【生产排障】"用户说答错了"——怎么在 10 分钟内定位是检索还是生成的锅？

- **考什么**：是否有可执行的归因路径。
- **新手答法**："看看回答。"
- **高手思路**：固定三步：① 查该次引用列表——空引用→检索层（进一步看是召回 miss 还是过滤过严）；② 有引用但内容不含答案→排序/分块问题（目标文档在库里但没进 top-K，或进了但 chunk 不含关键句）；③ 引用正确且含答案但回答错误→生成层（幻觉）。三步分别对应三层的修复手段。
- **落地要点**：把这三步做成排查 checklist；引用卡片展示四阶段排名的深意就在此（本项目的可解释引用设计）。

## 8. 工程视角：Demo 与生产的差距 + 架构演进

**Demo（LangChain 跑通）与生产的差距清单**：延迟（每环节预算与超时）、成本（embedding/rerank/生成三次模型调用的 token 记账与预算）、索引更新（文档变了增量重建 vs 全量）、权限隔离（检索过滤必须服务端强制，多租户下用户 A 检索不能命中用户 B 的向量）、多轮对话（指代消解与查询改写："它怎么配"要先改写成独立查询）。

**架构演进逻辑**（检索的"自主程度"递增）：

| 阶段 | 核心思想 | 代价 | 适用边界 |
|---|---|---|---|
| Naive RAG | 每问必检索一次 | — | 简单问答 |
| Advanced RAG | 查询改写、混合检索、rerank、上下文工程 | 组件多 | 生产标配 |
| Modular RAG | 检索成为可编排模块（路由、复用缓存） | 架构复杂 | 多源异构知识 |
| Self-RAG | 模型自我反思"要不要检索、答案是否被支持"（反思能力**训练内化**进权重） | 需训练 | 生成质量敏感场景 |
| Corrective RAG | **外部评估器**给检索结果打分，差的触发纠正（重查/网页兜底） | 额外评估调用 | 知识库质量参差 |
| Agentic RAG | Agent 决定**何时检索、检索什么、去哪检索、要不要再检索**（规划-工具-反思循环） | 延迟与不确定性最高 | 复杂研究型任务（法律/金融综合分析） |
| GraphRAG | 知识图谱组织文档，实体关系+全局归纳 | 建图成本高 | 关系密集、跨文档多跳推理 |

选型判断：从 Naive 起步，指标证明瓶颈在哪一层再引入对应的高级形态——Agentic RAG 解决的是"单轮检索不够"的问题，如果单轮检索 Recall 已 90%+，引入它只是徒增延迟。
