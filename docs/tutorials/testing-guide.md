# 功能测试指南：对话问答、知识库 RAG、MCP、诊断与补充测试全景

本指南回答"这个 Agent 项目应该怎么测"。第 0 章补概念，第 1 章对话问答，第 2 章 RAG，第 3/4 章 MCP 与诊断，第 5 章 Skill，第 6 章是**其他测试方式的全景清单**（韧性、并发、安全、预算、可观测性、性能、回归策略）——绝大多数验收点都可以对着界面逐条打勾。

## 0. 阅读前提：六个关键概念

### 0.1 什么是 RAG（检索增强生成）

大模型不知道你的私有文档，而且会"一本正经地编造"（幻觉）。RAG 的思路是：**回答之前先去知识库检索相关片段，把片段作为参考资料塞给模型**，让它"看着资料答题"。测试 RAG 的核心是三件事：**资料进得去**（索引）、**查得准**（检索）、**答案可追溯**（引用）。

### 0.2 混合检索的四个阶段（引用里的排名数字是什么）

| 阶段 | 通俗解释 | 擅长什么 |
| --- | --- | --- |
| **向量召回**（vectorRank/vectorScore） | 文本变向量，语义相近则距离近 | 懂语义、懂同义改写 |
| **BM25L 关键词召回**（bm25Rank/bm25Score） | 传统关键词匹配，统计词频 | 懂精确术语、类名、错误码 |
| **RRF 融合**（rrfScore） | 两路排名用 `1/(k+排名)`（k=60）合成总分 | 让两路互补 |
| **Rerank 精排**（rerankRank/rerankScore） | 专门的小模型重排 | 决定最终顺序，最准 |

> **为什么不能只用向量**：向量对精确标识符不敏感——搜 `NullPointerException` 时真正的异常类名可能被"语义相近"的内容挤下去。BM25L 恰好补上，所以两条路并行再融合。

### 0.3 MCP（Model Context Protocol）

让模型调用外部工具的开放协议。本平台用它接入**腾讯云 CLS 日志**：配置连接后模型能自主"查真实日志"。连接是用户级资产，只归配置者使用。

### 0.4 Plan-Execute-Replan（诊断执行模型）

诊断不是一问一答：**Planner**（检索 SOP 制定计划）→ **Executor**（真实调用工具取证）→ **Replanner**（看证据决定继续/转向/写报告）。每步证据持久化，报告结论可回溯。

### 0.5 渐进式 Skill

对话时只注入 Skill 的**名字和描述**；模型判断相关时才用 `load_skill` 工具加载正文。验证生效看两处：回答风格变化 + 工具调用区出现 `load_skill`。

### 0.6 LLM 用量预算

`llm.budget` 配置三道闸：单次输出上限、每用户每日 token 预算、全平台每月预算。超限返回 429 `BUSINESS_LLM_BUDGET_EXCEEDED`（HTTP 与 SSE 同码）。这是公开部署的成本防线，也是可测试的功能。

## 1. 对话问答测试

对话是最常用的链路，测试分五层：**基本能力 → 工具边界 → 多轮记忆 → 流式与渲染 → 量化评测**。

### 1.1 基本问答与工具调用边界（最重要的验收）

| 用例 | 操作 | 预期 |
| --- | --- | --- |
| 普通常识问答 | 问"用一句话解释什么是 HTTP" | 正常回答；**不**出现工具调用记录 |
| 实时信息 | 问"现在几点了" | 调用 `get_current_time` 工具后回答 |
| 知识库问题 | 上传文档后问其中内容 | 调用 `knowledge_retrieval`，回答带引用 |
| 闲聊 | 问"讲个笑话" | 不调用任何工具（避免每次都检索的过度工程） |
| 未上传任何文档时问知识问题 | 直接提问 | 回答**不带引用**、不编造来源 |

> **为什么"不调用"也是验收点**：Agent 的价值在于模型自主判断。如果闲聊也去查知识库，说明工具描述写得太宽，是检索质量问题而非功能问题。

### 1.2 多轮上下文与记忆

1. 两轮追问：先问"Milvus 是什么"，再问"**它**用什么协议通信"——模型应理解"它"的指代（上下文生效）。
2. 会话隔离：新开一个会话问同样问题——模型**不应该**记得上一会话的内容。
3. 记忆压缩（三种模式在输入框旁切换）：
   - 手动压缩：点「压缩」→ 生成摘要、上下文占用率下降、**完整历史消息不删除**（重新打开会话记录还在）。
   - 每 30 轮/70% 自动压缩：长对话持续使用后观察自动触发。
   - 95% 硬上限：把上下文逼满 → 提交被拒，提示"上下文已达到 95%，请执行手动压缩"，且**不写入该条消息**。

### 1.3 流式行为与中断

1. 回答以打字机节奏逐步出现（每字符约 28ms），不是一次性蹦出。
2. 回答完成后展开"工具调用"折叠区，工具生命周期（started→completed）完整。
3. **中断验收**：回答生成中刷新页面——重新进入后**没有半条助手消息**（要么完整要么不存在）。

### 1.4 渲染与交互

- Markdown：让模型输出表格/代码块/有序列表，均正确渲染；代码块有等宽字体和深色底。
- LaTeX：问"用行内公式和块级公式写出勾股定理"——`$...$` 与 `$$...$$` 均渲染为公式而非原文。
- 输入交互：Enter 发送、Shift+Enter 换行、中文输入法选词回车**不**误发送（IME 保护）。
- 反馈闭环：对回答点赞/点踩 + 填纠正内容 → 重新打开会话后反馈还在。

### 1.5 量化评测（进阶：让"回答质量"可度量）

人工点验适合功能验收；要度量**回答质量**需要评测集：

1. **构建黄金集**：整理 20~50 个问题，每个标注"期望回答覆盖的要点"（不是标准答案全文），存成 JSON。
2. **批量跑**：用脚本调用 `POST /chat/sessions/{id}/messages`（非流式端点）逐题获取回答。
3. **LLM-as-judge 评分**：让强模型对照"期望要点"给每个回答打 1-5 分并输出缺失点，汇总平均分与失败用例。
4. **回归**：每次换模型/调 Prompt/改检索参数后重跑，对比分数变化——这就把"感觉变好了"变成"分数从 3.8 升到 4.3"。

> 平台没有内置评测脚本（属于新增功能范畴），但黄金集方法只需要一个几十行的调用脚本即可落地；需要时可以基于 OpenAPI 契约快速写一个。

## 2. 知识库 RAG 系统测试

### 2.1 自动化测试（不需要任何真实凭据）

```bash
cd apps/backend
uv run pytest tests/test_hybrid_retrieval.py        # 检索算法：双路召回/RRF/精排边界
uv run pytest tests/test_knowledge_retrieval_tool.py # Agent 工具：租户过滤与空结果语义
uv run pytest tests/test_knowledge_documents_api.py  # 文档上传/校验/权限
uv run pytest tests/test_document_indexing.py        # 索引任务生命周期
```

### 2.2 端到端人工测试（真实模型 + 真实 Milvus）

**前置**：Docker 基础设施运行中、`user.project.json` 已填真实密钥、`/ready` 中 milvus 与 llm 为 ok。

| 步骤 | 操作 | 预期 |
| --- | --- | --- |
| 1 | `/knowledge` 上传 `.md`/`.pdf`（≤10MiB） | 文档出现，状态"待索引" |
| 2 | 选切分策略，看"切分预览" | 有界 chunk 列表；固定字符策略可调长度/重叠 |
| 3 | 创建索引任务 | 排队→执行中→成功；失败可见原因且可重试 |
| 4 | `/chat` 问只有该文档能答的问题 | 回答带引用卡片 |
| 5 | 展开引用详情 | 来源文档、chunk 摘要、四阶段排名/分数 |
| 6 | 删除文档 | 向量同步清理，再问同类问题无该引用 |

### 2.3 引用卡片验收（三步法）

1. **可追溯**：来源指向真实文档，摘要与回答对应。
2. **排名合理**：最相关片段 `rerankRank` 靠前；未命中的阶段显示"未命中"而非伪造 0 分。
3. **无命中即空**：问知识库里完全没有的问题——回答**不带引用**，宁可空手而归也不编造。

### 2.4 检索质量量化评测（进阶）

同 1.5 的黄金集思路，但评测对象是**检索**而非生成：为每个问题标注"应该命中的文档/chunk id"，脚本调用检索后计算 **Recall@5**（前 5 条引用里是否包含目标）与 **MRR**（目标片段的排名倒数均值）。切分策略调参（fixed 长度/重叠）前后各跑一次，用数字决定哪种策略更好。

### 2.5 权限隔离（安全验收）

双账号交叉：A 上传的文档，B 提问绝不能命中；B 在界面看不到 A 的文档列表。检索过滤在服务端强制附加，客户端参数无法越权。

## 3. MCP 连接：用途与测试

**用途**：把外部真实工具接入对话与诊断（内置场景：腾讯云 CLS 日志）。没有 MCP 模型只能背书，有了它能看真实数据。

| 步骤 | 操作 | 验收 |
| --- | --- | --- |
| 1 | 本机 CLS MCP Server 运行中（`:3000/sse` 可访问） | — |
| 2 | `/mcp` 新建连接（SSE + `http://127.0.0.1:3000/sse`） | 保存成功 |
| 3 | 点"检查" | 返回**真实工具列表**（非写死），状态更新 |
| 4 | 对话中问日志相关问题 | "工具调用"区出现真实调用记录（工具名/参数键/结果摘要/耗时），不是编造的日志 |
| 5 | 停用连接后重复提问 | 不再调用该工具 |

治理语义也是验收点：超时/重试有界、不同 server 同名工具明确报冲突、调用落审计。

## 4. 智能诊断（AIOps）：用途与测试

**用途**：从一条真实告警出发，自动完成"查 SOP → 定计划 → 取证 → 报告"，证据链持久化、结论可追溯、成功自动沉淀案例。

**前置三件套**：Milvus 健康、Alertmanager（`:9093`）可达、MCP 连接检查通过。

| 步骤 | 验收 |
| --- | --- |
| 发布演练告警 `uv run python scripts/publish_java_ecommerce_alerts.py`（外部副作用，显式执行） | Alertmanager 出现 10 条告警 |
| `/aiops` 刷新告警 → 从告警创建诊断 | 任务进入持久化后台执行，时间线实时更新 |
| 观察时间线 | Planner 计划 → 执行步骤 → 真实工具调用 → 证据卡片 → （可能）重规划 → 报告 |
| 检查报告 | 固定中文结构（告警清单/根因/处理方案/结论），结论带证据链接，证据不足处标注不确定性 |
| 知识闭环 | 成功诊断后在 `/knowledge` 出现自动生成的案例文档，下次提问可命中 |
| 可恢复性 | 执行中刷新页面，状态与事件从持久层恢复；可取消 |

不想碰真实云服务：`uv run pytest tests/test_aiops_diagnostics.py` 用假工具边界验证全流程逻辑。

## 6. 补充测试方式全景清单

除功能点验收外，一个生产级 Agent 系统还应覆盖以下九类测试。每类都给出在本项目中的具体做法。

### 6.1 自动化测试地图（回归的基础）

| 测试文件 | 覆盖什么 |
| --- | --- |
| `test_stream_rag_chat_api.py` | SSE 事件顺序、字符拆分、工具生命周期、引用隔离 |
| `test_chat_memory.py` | 记忆三模式触发边界（29/30 轮、69/70/95%） |
| `test_hybrid_retrieval.py` | 检索算法与各 provider 失败语义 |
| `test_aiops_diagnostics.py` | 诊断图、证据持久化、诚实 fallback |
| `test_llm_budget.py` | 预算边界（日界/月界/owner 隔离/估算标记） |
| `test_mcp_observability.py` | MCP 审计与脱敏 |
| `tests/protectedData.test.ts`（前端） | 认证头、SSE 解析、断帧 |
| `tests/chatLayout.test.ts`（前端） | 布局源码契约 |

跑法：后端 `cd apps/backend && uv run pytest`；前端 `npm run frontend:test`；契约 `npm --workspace packages/api-contracts run test`。**每次改动先跑受影响文件，提交前跑全量。**

### 6.2 API/错误码矩阵直测

不经界面直接 curl，验证统一 envelope 与错误目录：

| 用例 | 期望 |
| --- | --- |
| 无 token 调 `/chat/sessions` | 401 `AUTH_UNAUTHENTICATED` |
| 用 A 的 token 读 B 的会话 | 403 `AUTH_FORBIDDEN`（不泄露存在性） |
| 上下文打满后发言 | 409 `CHAT_CONTEXT_LIMIT_REACHED` |
| 预算调低后发言 | 429 `BUSINESS_LLM_BUDGET_EXCEEDED` |
| 上传超 10MiB 文件 / 非法类型 | 400/422 校验错误 |

每个错误响应都应含 `code/category/httpStatus/message/meta.requestId` 五要素。

### 6.3 安全测试矩阵

- **越权矩阵**：两个账号对读/改/删/列表逐项交叉（不只测读）。
- **XSS 输入**：让模型场景下在文档/Prompt 里放 `<img onerror>` 类内容——前端渲染必须剥离（自动化测试已覆盖 DOMPurify，可手工再验）。
- **日志脱敏抽查**：触发一次对话后在 `apps/backend/var/` 日志里搜索密钥前缀与用户提问原文——都不应出现（只允许 ID、状态、参数键）。
- **审计完整性**：每次工具调用在审计表有记录且不含参数值原文。

### 6.4 韧性/恢复测试（durable 语义）

1. **进程崩溃恢复**：索引任务执行中 `taskkill` 后端进程 → 重启 → 任务应从租约过期中恢复或显式失败可重试，不永久卡死。
2. **SSE 断开不取消**：诊断执行中关闭页面 → 任务继续跑完 → 重新打开页面看到完整结果。
3. **Milvus 停机降级**：`docker compose stop milvus` 后对话仍可用（检索工具显式报错而非编造），`/ready` 变 degraded 且逐项标明原因。
4. **取消语义**：执行中的诊断/索引点取消 → 状态机到 cancelled，不残留半态数据。

### 6.5 并发测试

- 两个账号同时各自发起对话与索引任务——互不串数据、互不阻塞（worker 并发领取）。
- 同一账号并发创建多个索引任务——任务队列按序处理，向量不互相覆盖。

### 6.6 性能基线（建立数字才能发现退化）

用秒表或脚本记录：**首 token 延迟**（发送到第一个字出现的时长）、**整答时长**、**检索耗时**（工具调用审计里的 durationMs）、索引 10 页 PDF 的总时长。记录当前基线数字，改动后对比。`/metrics` 提供进程级请求计数与平均耗时。

### 6.7 可观测性验证

- 任意请求的响应头/日志含贯穿的 `X-Request-ID`，报障时可用它精确定位单次请求全链路日志。
- `/ready` 各依赖项带延迟与安全错误信息；`/config/check` 区分"配置错误"与"依赖不可达"且不输出密钥。

### 6.8 前端专项

- 响应式窄屏（<860px、<640px）不破版、布局不溢出；`prefers-reduced-motion` 下打字点与过渡动画静止。
- IME 组合输入不误发、长文本滚动区域独立滚动不撑破页面（已有组件测试锁定）。

### 6.9 十分钟发布冒烟清单（每次部署/改版后必跑）

1. `/health` 200、`/ready` 全绿或明确 degraded。
2. 注册新账号 → 登录 → 发一条消息收到流式回答。
3. 上传一个小 `.md` → 索引成功 → 提问命中引用。
4. 打开 `/mcp` 检查连接 → 工具列表返回。
5. 界面无 console 报错、无"服务未连接"横幅。

## 7. 性能测试与优化（含实测案例）

功能测试回答"能不能用"，性能测试回答"快不快、扛不扛得住、瓶颈在哪"。方法论四步：**定义指标 → 建立基线 → 定位瓶颈 → 单变量优化后对比**。

### 7.1 指标定义（先有数字才能谈优化）

| 指标 | 含义 | 本项目测法 |
| --- | --- | --- |
| 首 token 延迟 | 发送消息到第一个字出现 | 秒表/脚本计时（网络+模型推理主导） |
| 检索延迟 | 一次知识检索的端到端耗时 | 工具调用审计的 `durationMs` |
| 每查询算法成本 | 检索中纯计算部分的耗时 | `scripts/bench_retrieval_bm25.py` |
| 吞吐/资源 | 并发请求数与内存占用 | `/metrics` + 任务管理器 |
| 包体积 | 前端首屏 JS 大小 | `npm run build` 输出 |

### 7.2 实测案例：BM25 语料缓存的 14 倍优化

**基线测量**发现：关键词召回每次查询都要 ① 从 Milvus 拉取该租户全量 chunk、② 对全语料重新分词、③ 重建 BM25L 评分器——三者都是 O(语料) 的每查询固定成本，随知识库增长线性恶化。

**瓶颈定位**：读代码确认调用链（`_keyword_recall` → `list_chunks` → `rank_bm25_documents`），排除法确认 Milvus/网络之外的纯算法部分可用合成语料独立测。

**优化实现**：新增 `Bm25CorpusCache`（按 租户+知识库集合 缓存 chunk、分词结果与评分器），语料分词与评分器构建在缓存填充时一次性支付；向量写入（索引完成）与删除路径显式失效缓存，TTL 兜底防遗漏；带文档过滤的查询按过滤后子集重建评分器（保证 BM25 的 IDF 语义正确）。

**前后对比**（`python scripts/bench_retrieval_bm25.py`，5 次取中位数，约 320 字/条的中文运维语料）：

| 语料规模 | 优化前 ms/查询 | 优化后 ms/查询 | 加速比 |
| --- | --- | --- | --- |
| 100 条 | 11.22 | 0.70 | 16.0× |
| 500 条 | 59.55 | 4.28 | 13.9× |
| 1000 条 | 128.51 | 9.28 | 13.8× |

之外还消除了每查询一次的 Milvus 全量拉取（网络+序列化成本，随语料规模增长）。

**诚实边界**：小语料下绝对收益有限（10ms 级），优化的价值在于**复杂度形状**——优化前每查询成本随语料线性增长，优化后与语料无关（只剩缓存失效时的一次性支付）；本基准不含网络因素，端到端延迟由模型推理主导。

### 7.3 其他已识别、未实施的优化点

- **MCP 工具发现缓存**：每次对话请求都做一次 MCP 工具发现（网络往返），可按用户缓存并在连接变更时失效——预计节省每请求数百毫秒（需权衡工具列表的新鲜度语义）。
- **前端 KaTeX 分包**：KaTeX 约 280KB 进入主 bundle，可动态 import 将其拆到懒加载 chunk——首屏（登录页）加载更快，首次进入对话时加载。
- **Milvus 首连初始化**：`/ready` 中 Milvus 首次检查 11 秒（建连初始化），可考虑应用启动时预热。

### 7.4 性能测试纪律

- 单变量：每次只改一个因素，否则对比无效。
- 多次取中位数，警惕首跑的冷启动效应（缓存预热、JIT 式效应）。
- 合成基准与端到端分开测：合成基准定位算法瓶颈，端到端验收用户感知。
- 记录环境（机器、负载、版本）——没有环境的数字无法复现。
