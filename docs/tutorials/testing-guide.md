# 功能测试指南：知识库 RAG、智能诊断、MCP 与 Skill

本指南整合三个常见问题的完整答案：如何测试知识库 RAG 系统；智能诊断与 MCP 连接有什么用、分别如何测试；如何用样例 Skill 验证对话的渐进加载能力。每个部分先讲机制再讲操作，难懂的概念都有补充解释。

## 0. 阅读前提：五个关键概念

### 0.1 什么是 RAG（检索增强生成）

大模型只认识训练数据里的东西，对你的私有文档一无所知，而且会"一本正经地编造"（幻觉）。RAG 的思路是：**回答之前，先去你的知识库里检索相关片段，把片段作为参考资料塞给模型**，让它"看着资料答题"。因此测试 RAG 系统的核心是三件事：**资料进得去**（索引）、**资料查得准**（检索）、**答案可追溯**（引用）。

### 0.2 混合检索的四个阶段（回答里的排名数字是什么）

本平台的每一条引用都带四组排名/分数，这是设计上刻意保留的"可解释性"：

| 阶段 | 通俗解释 | 擅长什么 |
| --- | --- | --- |
| **向量召回**（vectorRank/vectorScore） | 把文本变成一串数字（向量），语义相近的文本向量距离也近。"数据库连接池满了"能匹配到"DB pool exhausted" | 懂语义、懂同义改写 |
| **BM25L 关键词召回**（bm25Rank/bm25Score） | 传统关键词匹配算法，统计词频 | 懂精确术语、类名、traceId、错误码 |
| **RRF 融合**（rrfScore） | 把上面两路的排名用公式 `1/(k+排名)`（k=60）合成一个总分 | 让"懂语义"和"懂术语"的两路互补，谁也不偏科 |
| **Rerank 精排**（rerankRank/rerankScore） | 用一个专门的小模型把候选重新排序 | 决定最终展示顺序，最准 |

> **补充解释**：为什么不能只用向量检索？向量对**精确标识符**不敏感——你搜 `NullPointerException`，语义相近的"空指针异常"会命中，但日志里真正的异常类名可能排名靠后。BM25L 恰好补上这一点。两条路都查，再融合，就是"混合检索"。

### 0.3 MCP（Model Context Protocol）

一个开放协议，让模型能调用外部工具。本平台里 MCP 用来接入**腾讯云 CLS 日志服务**：配置连接后，模型可以自己决定何时"查日志"。MCP 连接是用户级资产——你配置的连接只有你能用。

### 0.4 Plan-Execute-Replan（智能诊断的执行模型）

诊断不是"一个问题扔给模型"。它是三阶段循环：**Planner**（先检索知识库里的 SOP 手册，制定排查计划）→ **Executor**（真实调用工具取证）→ **Replanner**（看证据决定继续查、调整方向还是写报告）。每一步的证据都持久化，报告里的结论能回溯到证据。

### 0.5 渐进式 Skill

对话时系统**只把 Skill 的名字和一句话描述**放进上下文（省 token）；当模型判断当前问题和某个 Skill 相关时，才通过 `load_skill` 工具加载完整正文。所以验证 Skill 生效要看两处：回答风格是否变化 + 工具调用区是否出现 `load_skill`。

## 1. 知识库 RAG 系统测试

### 1.1 自动化测试（不需要任何真实凭据）

```bash
cd apps/backend
uv run pytest tests/test_hybrid_retrieval.py       # 检索算法：双路召回/RRF/精排
uv run pytest tests/test_knowledge_retrieval_tool.py # Agent 工具：权限与空结果语义
uv run pytest tests/test_knowledge_documents_api.py  # 文档上传/校验/权限
uv run pytest tests/test_document_indexing.py        # 索引任务生命周期
```

这些测试用假模型验证逻辑正确性，CI 和本地都能跑。

### 1.2 端到端人工测试（真实模型 + 真实 Milvus）

**前置条件**：Docker 基础设施在运行（`docker compose -f infra/compose.yaml up -d`），`config/user.project.json` 已填真实模型密钥，`/ready` 中 milvus 与 llm 两项为 ok。

| 步骤 | 操作 | 预期结果 |
| --- | --- | --- |
| 1 | 打开 `/knowledge`，上传一个 `.md` 或 `.pdf`（≤10 MiB） | 文档出现，状态为"待索引" |
| 2 | 选一种切分策略，查看"切分预览" | 能看到有界的 chunk 列表（固定字符策略可调长度/重叠） |
| 3 | 创建索引任务 | 状态机流转：排队 → 执行中 → 成功；失败时能看到失败原因且可重试 |
| 4 | 到 `/chat` 提问一个**只有该文档能回答**的问题 | 回答附带引用卡片 |
| 5 | 展开引用详情 | 能看到来源文档、chunk 摘要、以及四阶段排名/分数 |
| 6 | 删除该文档 | 向量同步清理；再问同类问题不再出现该引用 |

### 1.3 如何读懂引用卡片（验收的核心）

点开任意引用，检查三点：

1. **可追溯**：来源指向真实文档，摘要与回答内容对应——模型不能"引用"不存在的资料。
2. **排名合理**：与问题最相关的片段，`rerankRank` 应该靠前；某阶段没命中的片段显示"未命中"而不是伪造 0 分。
3. **无命中即空**：问一个知识库里完全没有的问题，回答**不带引用**（系统宁可空手而归也不编造）。

### 1.4 权限隔离测试（安全验收）

注册第二个账号 → 上传不同的文档 → 用账号 A 提问：回答里**绝不能出现**账号 B 的文档内容；账号 A 在界面中也看不到 B 的文档。所有检索请求在服务端强制附加当前用户过滤，客户端无法越权。

### 1.5 常见失败与原因

| 现象 | 原因 |
| --- | --- |
| 索引一直失败 | Milvus 未启动（`docker compose ps` 查看）或 embedding 额度/密钥问题 |
| 提问无引用但文档已索引 | 问题与文档内容相距太远；先试文档里的原句 |
| 报"用量已达到预算限额" | 触发了 `llm.budget` 预算，管理员调整 `config/project.json` 后重启后端 |

## 2. MCP 连接：有什么用、怎么测

### 2.1 用途

MCP 连接把**外部真实工具**接到对话和诊断里，本平台的内置场景是腾讯云 CLS 日志查询：配置好后，你在对话里问"帮我查最近一小时的错误日志"，模型会自主决定调用日志工具、拿到真实结果再回答。**没有 MCP 时模型只能靠知识库和自身知识；有了 MCP 它能看真实世界的数据。**

### 2.2 测试步骤

1. 前置：本机 CLS MCP Server 在运行（启动脚本会拉起；单独验证可看 `http://127.0.0.1:3000/sse` 是否可访问）。
2. 打开 `/mcp` → 新建连接：传输 `SSE`，URL 填 `http://127.0.0.1:3000/sse`，保存。
3. 点击"检查"——**验收点：返回真实的工具列表**（不是写死的假列表），连接状态更新。
4. 到 `/chat` 问一个需要查日志的问题（如"查一下最近支付服务的错误日志"）。
5. 展开"工具调用"折叠区——**验收点：出现真实的 MCP 工具调用记录**（工具名、参数、结果摘要、耗时），而不是模型编造的日志内容。
6. 停用该连接后重复提问——模型不应再调用该工具（未启用的连接不参与）。

### 2.3 治理语义（也是验收点）

每次 MCP 调用都有审计记录（工具名、参数、结果摘要、状态、耗时）；调用超时/重试有上限；不同 server 的同名工具会明确报冲突而不是随机选一个。

## 3. 智能诊断（AIOps）：有什么用、怎么测

### 3.1 用途

给运维人员的"告警自动排查器"：从一条真实告警出发，系统自动完成"查 SOP → 定计划 → 查日志取证 → 必要时调整方向 → 生成带证据的报告"。报告的每个结论都能点回证据；成功的诊断还会自动沉淀为知识库案例，供下次检索。

### 3.2 前置条件（三样都要在）

| 依赖 | 检查方式 |
| --- | --- |
| Milvus（SOP/案例检索） | `docker compose ps` 中 milvus 健康 |
| Alertmanager（告警来源） | `http://127.0.0.1:9093` 可访问 |
| CLS MCP（日志工具） | `/mcp` 连接检查通过 |

### 3.3 测试步骤

1. 发布演练告警（**有外部副作用，由你显式执行**）：`uv run python scripts/publish_java_ecommerce_alerts.py`（向本机 Alertmanager 发布 10 条 Java 电商故障告警）。
2. 打开 `/aiops` → 刷新活跃告警——能看到真实告警列表。
3. 从某条告警"创建诊断"（或手写查询）→ 任务进入持久化后台执行，页面出现实时时间线。
4. **验收点（时间线）**：能看到 Planner 计划 → 执行步骤 → 真实工具调用 → 证据卡片 → （可能的）重规划 → 报告；每一步有状态。
5. **验收点（报告）**：报告为固定中文结构（告警清单/根因分析/处理方案/结论），关键结论带证据链接；证据不足处明确标注不确定性，而不是编造。
6. **验收点（闭环）**：诊断成功后，`/knowledge` 中出现自动生成的故障案例文档；下次提问相关问题能检索到它。
7. **验收点（可恢复）**：诊断执行中刷新页面/断开重连，任务状态和事件从持久层恢复，不丢进度；执行中可取消。

### 3.4 不想动真实云服务？

自动化测试 `uv run pytest tests/test_aiops_diagnostics.py` 用假工具边界验证计划/重规划/报告/证据持久化逻辑，不需要真实 CLS 凭据。

## 4. Skill 渐进加载测试

### 4.1 样例与验证要点

仓库 `samples/skills/` 下有四个现成的 `SKILL.md`（上传时选择文件本身，文件名必须严格是 `SKILL.md`）：

| Skill | 场景 | 上传后如何验证生效 |
| --- | --- | --- |
| `latex-writing` | 数学公式排版 | 问"用行内公式和块级公式写出 O(N log N) 和高斯求和"，回答应出现渲染后的公式而非 `$...$` 原文 |
| `code-review` | 代码评审 | 粘贴一段有缺陷的代码，回答应严格呈现"评审结论 / 问题清单 / 亮点"三段结构 |
| `sql-troubleshooting` | 慢 SQL 排查 | 描述"数据库很慢"，回答应从"第 1 步：明确现象"开始，一次只推进一步并反问 |
| `incident-brief` | 故障通报起草 | 给一次演练故障信息，缺失的信息应出现在"信息缺口"而不是被编造 |

### 4.2 操作步骤

1. `/chat` → 右侧「Skill 设置」→ 上传某个 `SKILL.md`（UTF-8 Markdown，≤ 64 KB）。
2. 勾选要启用的 Skill → 「保存使用的 Skill」。
3. 按上表提问验证。
4. **关键验收**：展开"工具调用"，看到 `load_skill` 被调用——证明正文是按需加载的，而不是一开始就全量注入（这就是"渐进式"的含义，省 token 且上下文更干净）。

### 4.3 补充解释：为什么我的回答"像"那个 Skill 了但没有 load_skill 记录？

初始上下文里有 Skill 的名字和描述，简单问题模型可能凭描述就能对答。这是正常行为；用更"深"的问题（如让 code-review 输出完整表格结构）通常能观察到 load_skill 调用。

## 5. 通用注意事项

- 所有用户可见数据按账号隔离，测试权限时永远用两个账号交叉验证。
- 用量预算（`llm.budget`）超限的报错是预期行为，不是故障。
- 公开部署实例上跑测试时，记住所有访客共享平台预算。
